# 消息总线与主线程成本

面板通过 Discourse 的 message-bus 接收新话题与生命周期事件。本文件规定订阅位置语义、订阅对站点自身位置的影响,以及站点长任务的成本归属判据。成本归属决定问题是否属于本项目范围:面板自身执行占用可忽略时,不得以修改面板刷新逻辑冒充对站点卡顿的修复。

**事实来源**:本机 discourse 源码克隆(只读,`2026.10.0-latest`)、gem `message_bus 5.0.0`、前端 `message-bus-client 4.6.0`(取自 registry,线上打包版本未核验)、以及四次浏览器内核级 trace(`perf/Trace-20261005T084754.json.gz`、`perf/Trace-20261005T104725.json.gz`、`perf/Trace-20261005T121135.json.gz`、`perf/Trace-20261005T153526.json.gz`,归一化输出为同目录 `*.comparison.json`、`*.input.json`)。

## 术语

**Channel Position / 频道位置**:
客户端在每个频道上记录的下标,表示已收到的最后一条消息 id。服务端按该位置决定回放范围。

**Backlog / 积压**:
保留窗口内、id 大于客户端频道位置的全部消息。

**Repositioning / 归位**:
服务端把某个频道的客户端位置直接置为该频道头部,并以 `/__status` 消息下发;该消息不改动 DOM,只改写位置。

**Loopback To Head / 回顶**:
面板把滚动位置恢复到信息流起点。

## 目标

- 面板订阅新话题与生命周期事件时不干扰站点自身的频道位置。
- 站点长任务的归属按 trace 直接判定,不依据调用次数或自测计时推断。

## 非目标

- 修复站点在 message-bus 回调内的同步渲染成本。该链路由 Discourse 核心与其主题决定。
- 在面板内实现积压回放或消息条数统计。
- 读取站点未公开的频道位置接口。

## 一、服务端位置语义

保留窗口由站点设置决定:Discourse 将 `max_backlog_size` 覆盖为 `100`(gem 默认 `1000`),`clear_every` 为 `50`(`config/discourse_defaults.conf:218`、`config/initializers/004-message_bus.rb:146-147`)。因保留窗口有上限,一次积压回放至多约百条。

`Client#backlog` 的位置分支(gem `message_bus 5.0.0`,已逐行核对):

```ruby
if last_client_id < -1            # lookbehind:相对总线头的回溯
  last_client_id = last_bus_id + last_client_id + 1
  last_client_id = 0 if last_client_id < 0
elsif last_client_id == -1        # 不请求积压
  next
elsif last_client_id == last_bus_id   # 已最新
  next
elsif last_client_id > last_bus_id    # 客户端超前于总线:重置为 -1
  @subscriptions[k] = -1
  next
end
```

规则:

- 频道位置只在两种情形下归位:订阅值为 `-1`;该频道存在客户端无权看见的消息(以 `new_message_ids` 记录)。
- 落后不触发归位。落后时服务端回放保留窗口内、id 大于当前位置的消息,客户端逐条推进位置。
- `-1` 的语义为「不请求积压,只收之后的新消息」。负数整体表示 lookbehind:`-2` 为最近 1 条及其之后,`-3` 为最近 2 条及其之后。

## 二、客户端分发语义

`message-bus-client 4.6.0` 的公开读面只有 `callbacks`,元素形状为 `{ channel, func, last_id }`;该版本不存在 `lastId`、`lastIdForChannel`、`lastIds`、`last_ids`、`channels` 五个属性(`dist:366-372`、`dist:513-517`)。

- `processMessages`(`dist:107-140`)外层遍历消息、内层遍历全部回调;命中频道即把该回调的 `last_id` 推进到该消息 id,并调用 `func`,不比较该回调自己的 `last_id`。因故同频道的积压消息会逐个触发该频道的全部回调,包括后注册的回调。
- `/__status` 在同一双层循环内处理(`dist:131-137`):把回调的 `last_id` 设为消息载荷里的频道值,不调用 `func`。
- 请求体每个频道的位置取该频道最后一个回调的 `last_id`(`dist:449-452`)。后注册的回调覆盖先注册回调的位置。
- 唤醒时 `onVisibilityChange` 清除 timeout 并立刻用原位置轮询(`dist:479-497`),不做位置重置。隐藏超过 20 分钟时 `shouldLongPollCallback` 转假,退化为后台轮询,期间位置继续陈旧。

## 三、面板的订阅约束

实现位于 `src/feed/controller.ts` 的 `_startSidebarIncomingTracking`、`_startSidebarTopicLifecycleTracking` 与 `_getMessageBusLastId`(`src/feed/controller.ts:823-933`)。

- 订阅频道为 `/latest`、`/new`(新话题与最新活动)与 `/delete`、`/recover`、`/destroy`(生命周期)。两组独立启停:停止 incoming 不影响其他排序视图的异常话题跟踪。
- 订阅位置的目标语义为取站点同频道的当前位置,不得传 `-1`。因「最后注册的回调位置覆盖先前回调」,传 `-1` 会把站点自身在这些频道的位置一并改为 `-1`,使服务端对这些频道不发积压并下发 `/__status`,站点因此静默丢失积压回放。当前实现未能取得该位置,故在 4.6.0 上仍以 `-1` 订阅,属已知偏差而非目标状态(见开放问题)。
- `_getMessageBusLastId` 依次尝试 `lastId`、`lastIdForChannel`、`lastIds`、`last_ids`、`channels` 五个属性;这五个属性在本机核对的 4.6.0 中均不存在,该函数因而恒返回 `-1`。控制器内不存在按 `callbacks[].last_id` 读取位置的代码路径(`src/feed/controller.ts:865-880`)。故在该 4.6.0 版本上,面板确实以 `-1` 订阅,上一条所述的位置覆盖副作用成立;线上打包版本若不同,该结论须重新核对(见 §七)。
- 面板的回调只登记候选并标记待筛选状态,不在此栈内重建列表;生命周期消息命中保留话题时才触发重渲染。

## 四、站点长任务的成本归属

判定依据为 trace 中按 URL 与函数归属的自耗时,不依赖 LoAF 读数:LoAF 对本脚本不可见,不能作为免责证据。

来自 `perf/Trace-20261005T084754.json.gz`(61.33s 录制,2,671,322 个事件):

- 主线程 `RunTask` 持续 11.858589 s,起点 8.298202 s。该任务由 message-bus 轮询响应带动(`https://ping.ldstatic.com/message-bus/…/poll` 的 `XHRLoad`)。
- 任务内两段并列:站点响应处理与同步渲染 5.500908 s(`chunk-hue237mp.digested.js:15:8071`),随后 `RunMicrotasks` 6.356479 s。
- 归属三分:本脚本 248.9 ms(0.41%,1,593 次调用,冻结窗口内累计 0.1 ms);其它脚本 584.2 ms;浏览器扩展 9,348.1 ms,其中 `bmnpopeennajofpobnoapccokbbppohj`(Bitwarden Password Manager)的 `bootstrap-autofill-overlay.js` 为 8,971.8 ms、64,436 次调用。
- 站点侧函数级热点:原生 `insertAdjacentHTML` 约 2.44 s(调用者 `insertHTMLBefore`),`lt` 约 1.38 s(其中 `lt ← lt` 自递归 1.37 s),GC 约 2.40 s,`countCategoryByState` 仅 58.2 ms。

来自 `perf/Trace-20261005T121135.json.gz`(禁用 Bitwarden 后的录制):

- 完整长任务 8,264.721 ms,起点 1.215117 s;站点 `FunctionCall` 7,634.898 ms,随后 `RunMicrotasks` 629.188 ms。本次全记录 Bitwarden 调用为 0。
- 采样热点为 `lt` 约 5,087 ms、`insertAdjacentHTML` 约 1,271 ms、GC 约 260 ms、`countCategoryByState` 36 ms。
- `perf/chunk-d5qas15v.digested.js` 的采样位置(零基 `lineNumber=3, columnNumber=7581`)对应 `[TAG_COMPUTE]()` 方法(`ot = Symbol('TAG_COMPUTE')`),调用链为 `evaluate → _execute → renderRoots → revalidate → flush`。故该热点为 Glimmer 依赖图的同步校验。
- 该录制的默认视图从相对 8.246275 s 开始,只覆盖长任务末尾约 1.23 s;查看完整录制须回到最上层时间范围。事件未被删除(`hiddenEntries` 为空)。

来自 `perf/Trace-20261005T104725.json.gz`(禁用 Bitwarden 后的对照录制):

- 主线程记录跨度 76.26 s,最长 `RunTask` 487.855 ms,最长 `RunMicrotasks` 524.156 ms;超过 1 秒的 `RunTask` 为 0(对照 08:47 的 11,858.589 ms 与 1 次)。故最长可见主线程事件为 524.156 ms 的微任务,大于所捕获的最长 `RunTask`,不得只报 487.855 ms 声称全部主线程工作短于该值。
- Bitwarden URL 的 `FunctionCall` 为 0(对照 64,440);全记录 MinorGC/MajorGC 区间并集 614.485 ms(对照 2,583.667 ms);侧边栏脚本 `FunctionCall` 1,745 次、最长一次 7.342 ms(对照 1,593 次、7.345 ms);捕获的 message-bus `XHRLoad` 为 1 次、最长 0.413 ms(对照 17 次、11,857.501 ms)。
- 统计口径:上述数值只针对页面 `CrRendererMain`,不含其他进程与子线程。`perf/Trace-20261005T084754.comparison.json` 的事件源为单个渲染进程的主线程(`perf/compare-wake-traces.py:59-62` 取 `renderers[main]`):其 `whole_trace.function_urls` 对 `bootstrap-autofill-overlay.js` 记 64,430 次,`whole_trace.bitwarden_calls` 按扩展 id 记 64,440 次;后者含该扩展在同一进程内的其它脚本,故包含前者,差值 10 次。上文「归属三分」中的 64,436 次出自整条 trace 的全线程排行(`perf/_cpu.txt:174`,标题为「自耗时排行(全线程,Bottom-Up)」),统计范围多出其它渲染进程,与 64,430 相差 6 次;该差值属统计范围差异,不表示同一范围内的调用次数不一致。三个数值均不等价于 `MutationObserver` 回调次数。
- 最长 `RunTask` 出现在相对 48.532 s,来源为话题请求 `/t/2983748.json?track_visit=true&forceLoad=true` 的响应处理,其中约 485 ms 为微任务与页面渲染;该任务不属于 message-bus 长回调。新记录仍有 17 个超过 50 ms 的 `RunTask`。
- 该对照不是相同消息与 DOM 状态的严格重放:只捕获到 1 次 message-bus 完成回调,故不得据此断言旧录制的 5.500908 s 全部由 Bitwarden 造成,也不得断言禁用扩展后已覆盖同规模唤醒补发。

08:47 录制中扩展侧的异常形态:同一观察回调在相同页面 frame 与 isolate 下由 13 个不同 `scriptId` 分别执行,每次 355.985～516.129 ms,累计 5,124.034 ms(含子调用;其中约 1,747.050 ms 为 MinorGC,两项不得相加);同一窗口全体 MinorGC 为 40 次、2,209.318 ms,这些 GC 分布于上述阶段内部,不得与 5,124.034 ms、5.500908 s、6.356479 s 相加,也不得将全部 GC 归因于 Bitwarden。`scriptId` 差异提示多个编译脚本实例的观察回调同时参与处理,重复注入与扩展重载后旧观察器未清理为待验证原因;`scriptId` 不能证明具体注入机制,也不等同于存活观察器数量。

判据:

- 站点在 message-bus 回调内的同步渲染为此类长任务的直接来源;面板的回调不重建列表,故面板自身不构成该任务的成本主体。
- 扩展对站点 DOM 变更的观察成本会放大该任务,但不解释站点部分。禁用扩展后站点链路仍可单独产生秒级阻塞。
- 定位具体组件前,不得以修改面板刷新逻辑作为该长任务的修复。

## 五、输入时延与滚动的关系

来自 `perf/Trace-20261005T153526.json.gz`(关闭侧边栏脚本后的对照):

- 主线程长任务 6,323.533 ms,起点 2.308427 s,由 message-bus 轮询 `XHRLoad` 带动;站点 `FunctionCall` 5,594.332 ms,随后 `RunMicrotasks` 728.758 ms。
- 窗口内 48 个 `GestureScrollUpdate` 全部含 `COMPONENT_INPUT_EVENT_LATENCY_RENDERING_SCHEDULED_IMPL`,输入至 frame swap 中位数 12.774 ms、最大 21.595 ms;页面进程合成线程记录 309 次 `DrawFrame`。同窗口鼠标事件进入主线程的等待最长约 6.15 s,`MouseDown` 等待约 1.85 s,页面 `EventDispatch` 为 0。

规则:

- 滚动既有已渲染内容的响应由合成线程承担,主线程阻塞期间该路径继续工作;新内容加载与楼层更新须等待主线程。
- 面板不得在话题滚动区安装可取消输入的处理器,否则滚动会额外等待主线程。规则与回归项见[滚动与输入路径](../feed/01-滚动与输入路径.md)。
- frame swap 是 trace 的显示管线节点,不等同于显示器真实发光时刻;比较须使用同一节点。

## 六、已核对与未核对的范围

已核对:

- gem 与 `message-bus-client` 的上述行号与语义(逐行核对源码原文)。
- 四次录制的主线程归属、长任务起止与采样热点。
- 本脚本在 61.33s 录制中 0.41% 的自耗时占比与冻结窗口内 0.1 ms。

未核对(见开放问题):线上实际打包的 `message-bus-client` 版本;`/__status` 在受限频道下的下发频率;站点侧 `max_backlog_size` 的实际生效值;chat 插件与其它插件的逐条订阅成本;面板在 `_getMessageBusLastId` 全部候选不可用时的回落行为对真实站点位置的影响。

## 七、开放问题

- 线上打包的 `message-bus-client` 版本未核验;上述 `dist:` 行号来自 registry 的 4.6.0。该版本若与线上不同,位置覆盖的副作用范围需重新核对。
- linux.do 实际生效的 `message_bus_max_backlog_size` 未知(站点设置可覆盖默认 100)。判定方法为探针在 lookbehind 下记录的 `span` 与 `holes`:连续分布说明保留窗口本身较小;稀疏分布说明保留较多但多数被过滤。
- 面板在 `_getMessageBusLastId` 全部候选不可用时回落 `-1`(`src/feed/controller.ts:865-880`)。该回落会在 4.6.0 上覆盖站点同频道位置;是否改为不订阅或延迟订阅,待取得可用位置的稳定读面后决定。
- 受限频道下 `/__status` 的下发频率,以及「后注册回调覆盖位置」导致的站点丢消息窗口长度,未量化。
- `bootstrap-autofill-overlay.js` 的调用次数有三处记载,口径各不相同:`comparison.json` 的 `function_urls` 记 64,430(单渲染进程主线程、精确脚本 URL);同文件 `bitwarden_calls` 记 64,440(同一进程、按扩展 id 统计,含该扩展其它脚本,比前者多 10 次);整条 trace 的全线程排行记 64,436(`perf/_cpu.txt:174`,范围含其它渲染进程,比 64,430 多 6 次,该差值属统计范围差异)。64,430 与 64,440 的来源脚本 `perf/compare-wake-traces.py` 已按 `:87`、`:98`、`:101` 核对;`perf/_cpu.txt` 的产出工具在仓库内没有文件记载 —— `.gitignore:13` 只登记 `tools/analyze-trace.cjs` 以 trace 文件为输入,未记载其输出,故 64,436 无法由当前仓库复算。
- 站点 chunk 为压扁的单行文件,采样中的 `lt`、`il`、`Gp` 等压缩名除 `lt` 外无法映射回源码函数名;消息条数无法由位置差还原,需在回调内计数。
- 跨进程的 `CpuProfiler::StartProfiling`(一次 3.31 s)属 DevTools 采样开销,位于非页面主线程;该开销与卡顿无因果关系,但录制期间会混入 trace。
