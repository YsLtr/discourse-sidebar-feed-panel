# 滚动与输入路径

面板话题区使用原生滚动,边界由 CSS 属性承担,不安装可取消输入的处理器。本文件规定该边界职责、禁止项及其理由,以及隔离夹具的验收项与未解限制。

**事实来源**:`src/ui/scroll.ts`、`src/styles/feed.css`(话题滚动容器规则)、`tools/check-scroll-isolation.py`;trace 证据见[消息总线与主线程成本](../../discourse/04-消息总线与主线程成本.md)§五。

## 术语

**Topic Scroll Area / 话题滚动区**:
承载 **Topic Item** 列表的滚动容器 `.sfp-feed-scroll`。该容器声明 `overscroll-behavior-y: contain` 与 `touch-action: pan-y pinch-zoom`。

**Category Bar / 分类栏**:
顶部可横向滚动的分类标签栏。该区域保留独立的 wheel 映射,不属于本文件的禁止项范围。

**Cancelable Input Handler / 可取消输入处理器**:
以 `{ passive: false }` 注册、可调用 `preventDefault()` 的 `wheel` 或 `touchmove` 监听。

## 目标

- 话题滚动区在手势开始时无需等待主线程确认是否取消默认滚动。
- 滚动串联由 CSS 承担,加载更多与阅读状态更新由 passive 监听观察。
- 上述行为由隔离夹具按真实实现验证,不以复制实现的方式测试。

## 非目标

- 消除站点自身 message-bus 回调造成的主线程长任务。该任务使新内容加载与楼层更新等待主线程,属既有独立问题。
- 让分类栏放弃 JavaScript:分类栏的纵向滚轮转横向滚动依赖脚本,不在本文件范围内。
- 为触摸设备提供额外的手势库或惯性滚动实现。

## 一、边界职责归属

- 话题滚动区声明 `overscroll-behavior-y: contain` 与 `touch-action: pan-y pinch-zoom`。该两条 CSS 规则承担上下边界与触摸行为。
- 话题滚动区只保留 passive 的 `scroll` 监听,用于触发加载更多与阅读状态更新。
- 面板不在话题滚动区安装可取消输入处理器。
- 平滑回顶的可中断路径使用 passive 的 `wheel`、`pointerdown`、`touchstart` 监听与捕获阶段的 `keydown` 监听(`src/ui/topic-list.ts:151-162`),仅用于中断动画,不调用 `preventDefault()`。

## 二、禁止可取消输入的依据

- 非 passive 的 `wheel` 处理器会使一次滚动手势的首个输入等待主线程,即便处理器自身执行耗时极短。因该等待与处理器内容无关,面板以「回调耗时很小」作为无影响的依据不成立。
- trace 实测:主线程长任务结束后 9.483912 s 派发的 wheel 事件耗时 0.333 ms,其子调用包含侧边栏脚本行号;关闭脚本后的对照录制中该位置不再出现脚本调用,而输入至 frame swap 的中位数从 5,882.854 ms 降至 12.774 ms(见 `perf/Trace-20261005T121135.input.json` 与 `perf/Trace-20261005T153526.input.json`)。
- 已渲染内容的滚动由合成线程推进,主线程阻塞期间继续工作;非 passive 处理器把该路径重新绑回主线程,故禁止项直接作用于输入时延。
- 分类栏的 wheel 映射保留:该映射改变滚动方向,属功能行为,不能由 CSS 承担(见开放问题)。

## 三、回归项

`tools/check-scroll-isolation.py` 把实际滚动实现与 CSS 提取到隔离 Chrome 夹具,断言 12 项:

- 上下边界的 wheel 不带动正文滚动。
- 内容短于视口时不带动正文。
- 触摸中段可滚动,上下边界与短列表不串联到正文。
- 重复绑定后底部只触发一次加载,阅读状态回调仍执行。
- 首次 wheel 无 renderer-main acknowledgement。
- 主线程被受控阻塞 1.4 s 期间,已渲染内容仍可滚动。

判定要点:

- 只有「首次 wheel 的 renderer-main acknowledgement 消失」区分新旧实现。Chrome 可能允许已开始的手势在旧实现下继续,故连续滚动延迟不作为判据;夹具须在页面忙碌前启动持续手势。
- 隔离夹具使用加载与状态回调桩,不重放真实站点的 message-bus 数据。夹具通过不构成真实站点输入时延改善的证据。

`--full-css` 诊断为可选项:在 Chrome 154.0.8037.93 上,2.2.3 与迁移后的完整 CSS 夹具都通过首轮次 wheel 检查,但两份夹具在主线程阻塞期间均未采到帧交换样本,因此都未通过忙碌窗口帧断言;仅容器规则的默认夹具通过全部 12 项(该录制有 97 个忙碌窗口样本)。该限制的成因未定位,断言不得放宽,也不得将完整 CSS 诊断报告为通过。

## 四、复现方式

```sh
npm run check:scroll
npm run check:scroll -- --full-css --label full-css
```

历史基线可直接指向旧版单文件:`python tools/check-scroll-isolation.py --source path/to/2.2.3.user.js --label baseline`。依赖 Python `websocket-client` 与本机 Chrome,可用 `--chrome` 指定浏览器路径。结果与小型测试 trace 位于被忽略的 `perf/scroll-isolation/`。

## 五、风险与回滚

- 删除非 passive 处理器后,若目标浏览器不支持 `overscroll-behavior-y`,边界串联行为依赖 `touch-action` 与容器高度,须以回归夹具复核;回归项覆盖短内容与上下边界两种情形。
- 回滚方式为恢复原处理器并同时恢复对应回归项,不得只恢复处理器而保留断言。

## 六、开放问题

- 完整 CSS 夹具在忙碌窗口未采到帧交换样本的成因未定位。已核对的是该现象在旧版与新版一致出现,故不归因于迁移。
- 分类栏 wheel 映射对输入时延的影响未单独测量。该区域需要 JavaScript 才能把纵向滚轮转换为横向滚动,若后续测量显示该映射成为阻塞点,须单独评估。
- 真实移动设备触摸、站点睡眠唤醒后的滚动行为未在本机验证;隔离夹具与 trace 都不覆盖物理触摸。
