# 稍后再读

**状态**：现行契约。行为以本文为准；实现位置见 §九 的 `file:line`。

**事实来源**：当前挂载与渲染路径（`src/ui/host.ts:389`、`src/feed/controller.ts:396`、`src/ui/topic-item.ts:166`、`src/feed/api.ts:36`、`src/platform/discourse.ts:72`）；Discourse 本机克隆（`lib/oneboxer.rb:308` 的 `local_onebox`、`app/controllers/onebox_controller.rb` 的 `requires_login`、`frontend/pretty-text/addon/oneboxer.js:79` 的请求参数、`frontend/discourse/app/initializers/inject-discourse-objects.js:14` 的 `service:current-user`、`lib/application_layout_preloader.rb:80` 的 `currentUser` 预载）。

**范围**：在 Feed Panel 的侧边栏内新增一个可持久化的「稍后再读」区域。面板关闭时区域随面板消失，数据保留；不改变信息流的查询、刷新与 incoming 逻辑。

## 术语

**Read Later Section / 稍后再读区域**：
侧边栏底部的第二空间，由一条可拖拽的分隔线与主列表分开。

**Read Later Item / 稍后再读条目**：
区域内的一个已保存链接。有 **Topic Snapshot** 的话题渲染为 **Topic Item**；其余渲染为 **Preview Card**。

**Divider / 分隔线**：
稍后再读区域顶部的可拖拽横线，同时是两侧高度的边界。

**Topic Snapshot / 话题快照**：
保存的紧凑 `Topic` 对象与 **Topic Display User**，用于渲染话题样式；每次主列表刷新后按 id 重新拉取并更新（§五）。

**Preview Card / 预览卡片**：
用 Discourse 编辑器同一个链接预览端点生成的紧凑卡片：头图、标题、摘要、分类徽章（§四.2）。

**Preview Availability / 预览可用性**：
本页是否登录的判定结果，决定要不要发 `/onebox` 请求。只在内存里，随页面刷新消失（§四.3）。

## 目标

- 页面内任意本站链接可直接拖入侧边栏底部；不经过设置面板，不新增 GM 键。
- 话题链接复用现有 Topic Item 的渲染与点击行为；其他链接使用编辑器内置链接预览的卡片。
- 列表作为「第二空间」固定在主列表下方，高度可拖拽并持久化；空态完全不存在。
- 条目自下而上排列，最新条目在最上方。
- 数据在多标签页之间保持一致，并随主列表刷新自我校正。

## 非目标

- 不做跨设备同步；不写 GM 存储、不写服务端。
- 不新增设置项；不改变信息流的刷新、筛选、排序、incoming 与阅读状态规则。
- 不实现移动端/触摸拖放：HTML5 拖放在触摸浏览器不可用，与面板既有的移动端非目标一致。
- 不后台轮询：只在主列表刷新、面板激活与跨标签页事件时同步。
- 不提供拖放之外的加入入口：不做菜单项、不做键盘加入（§十二 已裁定）。

## 一、加入与排列

### 1. 加入

- 同文档内拖动开始时，若 `dragstart` 的目标能解析到本站链接，底部出现矩形区域。
- 目标解析顺序：指针位置 → `event.target` 的最近 `[data-user-profile-link]` → 文本选区祖先（条目里的头像、昵称、用户名都是包在外层 `<a>` 内的 span；文本拖拽时 `target` 会被重定向到整张卡片，所以直接取 `closest("a[href]")` 只会得到话题链接）；都不中再退回 `closest("a[href]")`。
- 从其他标签页/地址栏拖入时，`dragenter` 命中侧边栏且 `dataTransfer.types` 含 `text/uri-list` 才显示。
- 空列表：矩形是虚线遮罩，文案「拖进加入稍后再读」。非空：区域已存在，指针进入后文案变「松开加入稍后再读」、边框与底色加深。
- 松开：读取地址——只有「从发布者链接拖出」时才用 `dragstart` 记录值（浏览器给整张卡片准备的 `text/uri-list` 是话题链接），其余用 `text/uri-list`（退回 `text/plain`），重新校验同源后加入。
- 加入的是话题且主列表已有该话题时，直接复制主列表的 `Topic` 与发布者，**不再发补全请求**；渲染立刻是话题条目。
- **已在列表里的链接再拖一次 = 移到最新位置**（`store.add` 合并而非覆盖）：新记录没带 `preview`/`topic`/`user` 时保留旧值，所以重拖不会把预览抹掉，也不会重复请求。
- 拖到侧边栏其他位置：`dragover` 仍 `preventDefault()`，但 `drop` 不加入——避免浏览器把链接丢进面板时执行页面导航。
- 拖拽取消（`dragend`、离开侧边栏、离开窗口）：清理高亮；空列表时收起区域。

### 2. 排列

- 存储顺序、DOM 顺序、视觉顺序三者一致，都是「新 → 旧」：`items[0]` 是最新加入的，排在最上方。
- 整块列表钉在区域底边，新条目从上方插入、把旧条目往下顶，所以看起来是「往上长」：

```text
┌ 分隔线
│ 最新条目      ← 新加入的出现在这里
│ 较新的条目
│ 最早的条目    ← 底边（主轴起点，scrollTop = 0）
└
```

- 贴底与滚动原点都由 `.sfp-rl-scroll` 的 `flex-direction: column-reverse` 提供。它只负责「整块贴底」，**不反转条目**——`.sfp-rl-list` 自身仍是正常 `column`。
- 内容不足时自动贴底；内容溢出时 `scrollTop = 0` 就是贴底，往上滚是负方向——**从下往上算**，与普通列表相反。
- 正因为原点在底部，改变区域高度只让上方多露出内容，条目一步都不动（§八.2 第 5 条）。
- 与主列表的区别只在「生长方向」：主列表向下堆，这里向上堆。
- 存储版本 2 的数组是「新 → 旧」；读到版本 1（旧 → 新）时整体反转一次再存回。

### 3. 打开、移除与排序

- 话题条目沿用 `createTopicItem` 的点击/中键逻辑（SPA 导航、新标签页、头像与用户名入口）；打开时把快照标记为已读并持久化。
- 预览卡片条目使用普通 `<a>` 导航（整页刷新），不对未知路由做 SPA 假设。
- 打开后**不自动移除**。
- **移除 = 把条目拖出区域**：没有删除按钮，也没有悬停提示文案（提示会跟着条目一起被拖，纯噪音）。
- **排序 = 把条目拖到别的条目上**：拖动中源条目半透明，目标位置画一条 `--tertiary` 边线（只画 `box-shadow`，不动布局，列表不抖）。
- 区域内的拖动带私有类型 `application/x-sfp-read-later`，与外部链接区分开：内部拖动不显示加入遮罩、不触发补全请求，松手只重排或删除。
- 移除最后一条后区域收起，**同时丢弃拖动过的高度**——下次加入时又按「一个条目高」出现，回到初始状态。

### 4. 空态

- 没有条目时区域 `hidden`，主列表恢复完整高度。
- 分隔线、提示文案都不出现。
- 拖拽中才临时显示区域，指示框盖住整个区域（见 §七.2、§七.4）。

## 二、数据与持久化

### 1. 键与位置

- 使用 `localStorage`；它按 origin 自动隔离，正好对应一个 **Discourse Site**。
- 键：`sfp_read_later_v1`（列表）、`sfp_read_later_height_v1`（用户拖出的高度，px；`null` 表示从未拖动）。
- 列表文件带 `version`：`2` 表示数组是「新 → 旧」；读到 `1`（旧 → 新）时反转一次。数组顺序就是视觉顺序，索引可以直接用于排序。
- 不写 GM；键定义放在 `src/read-later.ts` 而不是 `src/storage-keys.ts`——后者是 GM 键与 `SITE_SCOPED_STORAGE_KEYS` 的登记处，混放会诱使有人把这两个键加进 GM 迁移列表。

### 2. 记录结构

```ts
interface ReadLaterItem {
  url: string; // pathname + search + hash，同源相对地址
  title: string; // 拖拽时抓到的纯文本标题，作为预览标题的兜底
  kind: "topic" | "link";
  topicId?: number;
  addedAt: number;
  topic?: Topic; // 列表接口返回的紧凑 Topic；补全失败时缺省
  user?: TopicUser; // 首个 poster
  preview?: {
    // 编辑器内置链接预览抽取出的字段，见 §四.2
    title?: string;
    excerpt?: string;
    imageUrl?: string;
    badge?: string;
  };
}
```

存储值为 `{ version: 1, items: ReadLaterItem[] }`。`availability`、`failedUrls` 与排队状态都不进这里：它们是页内状态（§四.3）。

### 3. 规则

- **同 URL 移到最新**：再次加入时合并——新记录缺 `preview`/`topic`/`user` 就保留旧值，然后把整条提到数组头部。重拖既改位置又不丢预览。
- **上限**：200 条；超出丢弃最旧（数组头部）。
- **读取校验**：逐条要求 URL 可解析、`http(s)`、同 origin、`addedAt` 合法；非法条目静默丢弃。这样即使 localStorage 被改写，也不会渲染 `javascript:` 或跨站链接。
- **损坏/未知版本**：按空列表处理，下一次写入重建。
- **写入失败**（配额或隐私模式）：丢弃最旧的一半重试一次；仍失败则仅保留内存态并 `console.warn`，本次会话仍可增删。
- **高度**：保存用户拖出的值（px）；渲染时按 §八.2 钳制。窗口变大后恢复用户值；`null` 时走 §八.3 的自动高度。

### 4. 话题快照的来源

- 拖拽时话题已在 `ResidentTopics` 中：直接使用驻留的 `Topic` 与 **Topic Display User**，不发请求。
- 否则请求 `/latest.json?topic_ids=<id>`，复用 `createFeedApi.byIds`，不新增 API 形态；取 `topic_list.topics` 中 id 匹配的项与 `users` 中首个 poster。
- 请求使用独立的 `AbortController` + 8 s 超时，并随 `viewScope` 一起中止；失败、超时或取消则按 `kind: "topic"`、无快照保存，渲染走 §四.2 的预览卡片。
- 只保存列表接口的紧凑对象，不保存 `post_stream` 等完整话题 JSON。

## 三、跨标签页同步

- 监听 `window` 的 `storage` 事件（只在**其他**标签页写入时触发），随 `viewScope` 注册与释放。
- `event.key` 为 `sfp_read_later_v1` 时：重新读取并校验整份列表，替换内存态并重渲染；贴底由 `column-reverse` 保证，不需要额外校正。
- `event.key` 为 `sfp_read_later_height_v1` 时：更新 `desired` 并重新应用高度，不改列表。
- `event.key === null`（其他标签页 `localStorage.clear()`）按空列表处理。
- 写入方自身不收到事件，因此不需要去重比较；若同一份内容被另一标签页重复写入，重渲染是幂等的。
- 冲突策略：最后一次写入生效；不做字段级合并。

## 四、渲染

### 1. 话题条目

- 复用 `createTopicItem(topic, false, { href, user, onActivate })`：新增可选第三参，`href` 覆盖 `_topicListUrl`（保留楼层号），`user` 覆盖驻留用户查找，`onActivate` 取代默认的 `markTopicAsRead`。
- 外层包一个 `position: relative` 的 `.sfp-rl-item`（`data-url` 即排序与删除的键）；条目本身仍是 `<a>`，拖动起点落在这层上。
- 分类徽章、标签、统计、时间、未读点全部沿用现有规则；快照缺字段时按渲染器现有逻辑降级。
- 话题被标记为异常时（§五），沿用 `sfp-topic-unavailable` 样式与 `t("topicUnavailable")` 提示。

### 2. 预览卡片（其他链接与无快照的话题）

- 数据来自 Discourse 编辑器自己的链接预览端点，而不是我们另写的抓取：

```text
GET /onebox?url=<encodeURIComponent(绝对地址)>
```

- 该端点就是编辑器预览用的那个（`frontend/pretty-text/addon/oneboxer.js:79`），服务端 `Oneboxer.local_onebox`（`lib/oneboxer.rb:308`）对本站 URL 走本地模板，**不发外网请求**：
  - 话题 → `aside.quote`：头像、标题、分类徽章、首楼摘要；
  - 用户 → `aside.onebox.user-onebox`：头像、`@username`、姓名、简介、加入时间；
  - 分类 → 分类 logo、名称、描述；
  - 其他本站路由（`/about`、`/u/x/activity` 等）→ 纯 `<a>` 兜底。
- 服务端约束（决定我们的调用方式）：
  - `requires_login`（`app/controllers/onebox_controller.rb:4`）：匿名请求失败；
  - 同一用户同时只允许一个预览（`Oneboxer.is_previewing?`，`:14`）→ 429，请求串行排队（间隔 150 ms），遇 429 等 2 s 重试一次；
  - `recently_failed?`（`:22`）→ 404，同一 URL 本次页面不再重试；
  - `refresh` 不为 `true` 时先查 `Oneboxer.cached_preview`（`:7-11`）。
- 请求形状照抄编辑器（`frontend/pretty-text/addon/oneboxer.js:79`）：`?url=…&refresh=true`，带 `X-CSRF-Token`、`X-Requested-With: XMLHttpRequest`、`credentials: "include"`。**`refresh=true` 不能省**：服务端缓存按 URL 只存一份，曾经缓存下来的纯 `<a>` 兜底会一直生效，表现就是「个人资料预览不出来」。`category_id`/`topic_id` 只有话题预览用得上（`lib/oneboxer.rb:365`），我们从不 onebox 话题，故不传。
- 客户端只抽取字段，**不保存 HTML**：用 `DOMParser` 解析响应，先找 `aside` 或 `.onebox` 容器，再按以下顺序取值（一律用 `textContent`，再折叠空白）：
  - 头图：第一个 `img` 的 `src`（仅接受 `http(s)` 绝对地址）；
  - 标题：`.quote-title__text-content a` → `.onebox-body h3 a` → `a` 文本；
  - 摘要：`blockquote` → `.onebox-body p` → `.description p`，截断 200 字符；
  - 徽章：`.badge-category__name` 文本。
- **200 不等于成功**：`Oneboxer.local_onebox` 在本地模板拿不到内容时返回纯 `<a href='url'>url</a>`（`lib/oneboxer.rb:328`），控制器只判 `preview.blank?`，所以这种兜底也是 200。编辑器把它当失败（`frontend/discourse/app/static/prosemirror/extensions/onebox.js:694` 用正则匹配同一种形态），提示「无法加载预览」。我们照同一条线判：拿不到 `aside`/`.onebox` 容器就算失败，走降级卡片。
- 渲染：40 px 圆角头图 + 标题（最多两行）+ 摘要（最多两行）+ 徽章；`dir="auto"`。

### 3. 预览可用性与降级

`/onebox` 要登录、还有 429 单飞限制；而登录态在页面里已经有现成答案，读它不花请求，所以**先探测再决定发不发**。

- 探测一次、页内缓存：`activateFeed` 时调 `discourse.isLoggedIn()`（`src/platform/discourse.ts` 新增）。它内部先读 `__container__.lookup("service:current-user")`——与 `src/platform/discourse.ts:72` 读 `service:message-bus` 同一条路径；该注册值就是 `User.current()`（`frontend/discourse/app/initializers/inject-discourse-objects.js:14`），匿名时为 `null`。
- 结果写进页内状态 `availability: "available" | "unavailable"`，**随页面刷新消失**，不写 localStorage、不跨标签页共享：
  - 取到带 `id` 的用户 → `available`；返回 `null` → `unavailable`；
  - `lookup` 抛错或容器不存在 → `isLoggedIn()` 退回读 `#data-preloaded` 的文本（`lib/application_layout_preloader.rb:80` 只在登录时写入 `"currentUser"` 键，搜 `"currentUser":` 即可，无需解析整块 JSON）；仍判断不了 → `unavailable`（宁可不发请求）。
- 只有 `availability === "available"` 才发 `/onebox`；`unavailable` 直接渲染降级卡片，一次请求都不发。
- 运行中收到 403（探测说登录但服务端不认，例如会话过期）：把 `availability` 翻成 `unavailable`，本次页面不再发请求。
- 失败去重：`failedUrls: Set<string>` 记录本页已失败的 URL（任意状态码），同一 URL 不再重试；随页面刷新消失。
- **成功的预览按 URL 缓存**（`previewCache`）：条目被拖出删除后 `item.preview` 随记录一起消失，再加回来直接复用缓存，不再发一次 `/onebox`。只缓存成功结果——失败不进缓存，重加即重试。
- **页内状态跟着列表走**：每次渲染把 `requestedUrls`/`failedUrls`/待发队列里「已经不在列表里」的 URL 清掉，否则删掉一条再加回来会被上次的失败永久挡住——条目还在，却既不请求也没有缓存可用。

#### OG 回退（onebox 拿不到卡片时）

`/onebox` 返回 200 但没有 `aside`/`.onebox` 容器时，先不退成降级卡片，而是**再取一次目标页自己的 `<head>`**，读 `og:title` / `og:description` / `og:image`：

- 只截到 `</head>` 就返回（`fetchPageHead`）：整页 ~800 KB、head 只有 ~53 KB，少传 90% 的字符串，解析从 8 ms 降到 1 ms（实测 linux.do，见 §十三）。
- 同源 GET、`credentials: "include"`、不加任何新权限；**只对本站链接用**——外站会被 CORS 挡死，绕过就得加 `@connect` + `GM_xmlhttpRequest`，等于把权限面扩到任意站。
- 有结果就缓存进 `previewCache` 并替换卡片；仍拿不到才记进 `failedUrls`。
- `external_onebox`（`lib/oneboxer.rb:524`）帮不上忙：它只处理**外站** URL，而本功能只收同站链接；同站走 `local_onebox`（`lib/oneboxer.rb:308`），它无论如何都返回非空 HTML（最差是纯 `<a>` 兜底），所以 `onebox_raw` 的 `|| external_onebox` 那一支对同站链接永远不触发。

- 降级卡片：不加载 favicon，也不留空图位。头图位置换成通用链接图标，标题用 `item.title`（缺失时取路径末段），并显示 `t("linkPreview")`（链接预览 / Link Preview）作为说明。匿名与失败两条路径都不产生额外请求。

### 4. 不显示加载态

预览在补全前就按降级卡片渲染（标题 + 链接预览说明），补全成功后原地换成预览卡片。**列表里没有「加载中」行**：它占高度、还会让人以为整个区域在等网络，而实际上只有那一条的卡片在等。

## 五、刷新同步

主列表每次成功刷新后，稍后再读区跟着校正一次。

- **触发点**：`loadTopics()` 首页成功、`_refreshCurrentView()` 成功、`activateFeed()` 挂载完成。三者共用 `readLater.sync()`。
- **增量刷新**：最新活动视图下的静默刷新走 `_applySidebarIncomingTopics()`，只取 incoming 那几个 id。这批数据是**已经取到的**，因此直接用 `mergeTopicSnapshot()` 覆盖命中条目的快照，**不发任何请求**；这一轮没取到的话题保持原样，不猜、不补拉。`_handleSidebarTopicLifecycleMessage()` 的阅读状态推送同理不碰条目。
- **拉取**：主列表里已经有的话题**不发请求**，直接用常驻窗口里的那份；只有主列表没有的才收集成 id，按 50 个一组调用 `api.byIds(chunk)`（`src/feed/api.ts:56`），最多 4 组（与 200 条上限一致）。请求挂在 `viewScope` 的 `AbortController` 上，面板关闭即中止。
- **合并**：返回的话题按 id 覆盖 `item.topic`，并同步 `title`（取 **Topic Display Title**）；`user` 用响应里的首个 poster 更新。`addedAt`、`url`、顺序不变。
- **消失**：请求成功（HTTP 200）但响应里没有该 id → 对快照调用 `markUnavailable`（`src/feed/unavailable.ts:4`），与主列表同一套异常标记；再次出现时清除标记。请求失败、429 或中止时**不标记**，避免把网络问题当成删除。
- **渲染**：一轮同步结束后重渲染区域（列表很短，整段重建比逐条打补丁简单）。
- **写入**：一轮同步只写一次 localStorage，内容未变化则跳过。
- **频率**：主列表刷新本身受既有节流（`AUTO_LOAD_*`、自动刷新间隔）约束，同步不额外加定时器。

已知代价：`/latest.json?topic_ids=` 只返回当前用户可见的话题，未列出、私密或已删除的话题会被标为异常；再次可见后自动恢复。这与主列表的异常检测口径一致。

## 六、链接识别

```ts
parseReadLaterLink(raw: string, origin: string):
  { url: string; kind: "topic" | "link"; topicId?: number } | null
```

- 用 `new URL(raw, origin + "/")` 解析；拒绝解析失败、非 `http(s)`、`origin` 不等、纯 `#fragment` 与空 href。
- 话题路径按段解析，而不是单条正则：

```text
/t/123                → topic 123
/t/slug/123           → topic 123
/t/slug/123/5         → topic 123，保留完整 URL（含楼层号）
/t/123/5              → topic 123
/t/slug/notanid       → link
```

判定顺序：`/t/` 后第一段为数字且第二段也为数字时取第一段；第一段非数字且第二段为数字时取第二段；只有一段且为数字时取该段；否则按 link 处理。这样同时覆盖带 slug、不带 slug 与带楼层号的形态。

- 其他本站路径（`/u/...`、分类、任意页面）一律 `kind: "link"`，交给 §四.2 的预览卡片。
- 归一化为 `pathname + search + hash`；不做尾斜杠归一，避免把不同 URL 合并。
- 标题提取顺序：`.sfp-topic-title-line` 文本（面板自己的条目）→ `title` 属性 → 链接文本 → 路径末段；折叠空白、截断 300 字符。渲染时使用 `textContent` 或 `escapeHtml`。

## 七、拖放实现

### 1. 事件

- `document` 捕获阶段 `dragstart`：
  1. 若起点在 `.sfp-rl-item` 内 → **内部搬动**：记下 url、打上私有类型 `application/x-sfp-read-later`，不显示加入遮罩。
  2. 否则先找发布者链接，顺序是：指针位置（`elementFromPoint(clientX, clientY)` 的最近 `[data-user-profile-link]`，最准）→ `event.target` 的最近祖先 → 文本选区祖先。三步都是因为文本拖拽时 `target` 会被重定向到外层 `<a>`（整张卡片），直接 `closest("a[href]")` 就得到话题链接。
  3. 都没有则退回 `closest("a[href]")`；连链接都不是（例如分类标签拖拽）就不显示区域。
- `container` 的 `dragenter`/`dragover`：外部拖入时 `types` 含 `text/uri-list` 才显示/高亮；`dragover` 一律 `preventDefault()`（防止链接丢进面板时浏览器导航），但只有分隔线以下区域接受 `drop`。
- 内部搬动时 `dragover` 只认区域本身，按指针 `clientY` 与各条目中线算插入下标，给目标条目画边线。
- `section` 的 `drop`：外部链接按 §一.1 取地址重新走 `parseReadLaterLink`；内部搬动则重排或删除。
- `document` 的 `dragend`、`drop`、离开窗口的 `dragleave`：清理高亮、插入线与记录的地址；空列表时收起。
- 所有监听通过 `viewScope.listen` 注册；`deactivateFeed` 时随 scope 释放。

### 2. 两种拖拽必须分开

外部链接与内部条目的拖拽看起来一样，但语义相反：前者「加入」，后者「搬动/删除」。区分手段是私有 MIME 类型 `application/x-sfp-read-later`：

- 区域内的 `dragstart` 写入它，`dragover`/`drop` 见到它就切到搬动分支，不显示加入遮罩、不触发补全请求。
- 拖出区域（`dragleave` 到容器外）且没有落在区域内 → 视为删除。
- 落在区域内 → 按插入下标重排：DOM 下标就是存储下标（两者都是「新 → 旧」），只需按「先摘出自己」修正一次，再调 `store.move(url, index)`，顺序持久化。

### 3. 为什么不在 dragover 读 URL

拖拽期间 `DataTransfer.getData()` 返回空字符串（保护模式），只能读 `types`。因此「是否是本站链接」的最终判定放在 `drop`，拖拽期间只按 `types` 显示目标。

### 4. 拖拽中不重渲染

`dragstart` 里只切换区域的可见性与遮罩，**绝不重建条目节点**：把正在被拖的节点从文档里换掉，浏览器会取消这次拖拽（图片拖拽因为数据已抓取才侥幸存活，文本拖拽直接失败）。所以列表的 `render()` 与拖拽开始是两条独立路径。

### 5. 遮罩文案分两段，落点范围只限区域

两段文案与高亮都必须由「落点是不是这个区域」驱动，所以判定分两层：

- 拖拽开始、指针还没进区域：显示 `t("readLaterDropHint")`（拖进加入稍后再读），虚线边框、无底色。
- 指针进入区域（`dragover` 落在 `section` 上）：显示 `t("readLaterDropRelease")`（松开加入稍后再读），边框转 `--tertiary`，底色 `color-mix(in srgb, var(--tertiary) 12%, transparent)`。
- 容器的 `dragover` **只负责让区域出现并 `preventDefault()`**，绝不设置高亮：拖拽起点本来就在容器（侧边栏）里，用容器判定会让区域在拖拽刚离开链接的瞬间就亮起来，等于把整个侧边栏都算成落点。
- `dragleave` 的 `relatedTarget` 落在区域外就撤回高亮，退回「拖进」文案。

### 6. 跨文档拖入

- 从另一个同源标签页拖入时没有本页 `dragstart`；`dragenter` 的 `text/uri-list` 触发显示，`drop` 时按同源校验。
- 标题取 `text/plain`（若不是 URL）或 URL 路径；预览与快照照常补全。

## 八、布局与分隔线

### 1. 结构

```html
<div class="sfp-feed-container">          <!-- 既有 flex column -->
  …header / tabs / filter…
  <div class="sfp-feed-scroll">…</div>    <!-- flex: 1 -->
  <div class="sfp-rl-divider" role="separator" tabindex="0" hidden></div>
  <section class="sfp-read-later" hidden> <!-- flex: 0 0 auto; height: Npx -->
    <div class="sfp-rl-scroll"><div class="sfp-rl-list">…</div></div>
    <div class="sfp-rl-drop" hidden></div>  <!-- absolute 遮罩 -->
  </section>
</div>
```

- 分隔线与区域都追加到 `host.feedContainer` 末尾，**分隔线是区域的兄弟节点**，不属于任何一侧：线上方是主列表，下方才是稍后再读。区域没有 `border-top`，唯一的边界就是这条线。
- 分隔线自身就是那条线：3 px 高、无内边距、无 `::before`、无背景留白，所以它不占任何多余空间，也不遮挡两侧内容。hover、focus、拖拽时变 `--tertiary`。
- 命中面积由两个**不可见的小圆**撑开（`.sfp-rl-grip`，直径 30 px = 线高的 10 倍、`border-radius: 50%`、透明）：一个在线的中心（`left: 50%`），一个在右端（`right: 0`，右边与宽度分割线相切）。它们比线高，上下各多出 13.5 px；做成圆而不是整条，是为了尽量少挡住两侧条目的点击。圆是分隔线的子节点，`pointerdown` 冒泡回分隔线，拖拽逻辑不用改一行。
- 圆要**两侧都能命中**，得靠 `z-index: 2`：区域是 `position: relative` 且有背景，DOM 上又在分隔线之后，不抬高的话伸进区域的那一半会被背景吃掉点击。
- 右端的圆与线的右边缘相切（`right: 0`），整圆落在区域内，不与右侧的宽度把手抢位置。
- `.sfp-rl-scroll` 是独立滚动容器（`overflow-y: auto`、`overscroll-behavior-y: contain`、`touch-action: pan-y pinch-zoom`），滚动条与主列表共用同一套变量（`--scrollbarThumbBg`、`--scrollbarWidth`、`scrollbar-gutter: stable`），两侧看起来是同一个列表。
- 它还必须 `display: flex; flex-direction: column-reverse`——这是贴底与「从下往上算」的唯一手段，不用 `margin-top: auto`（那会在「放得下」与「放不下」之间换一次对齐方式，拖分隔线时内容就跳）。它只有 `.sfp-rl-list` 一个子元素，所以「反转」作用在整块列表的定位上，不会颠倒条目顺序；`.sfp-rl-list` 自身保持 `column`，DOM 顺序就是从上到下的视觉顺序。
- 拖拽指示框是 `position: absolute; inset: 2px; z-index: 3` 的遮罩，覆盖**整个区域**并压在条目之上，`pointer-events: none` 所以不吃事件；它不参与列表排版，因此不会把条目挤走，也不会只在列表底部露出一条。
- 宽度把手的命中区：5 px 的把手同样太细，里面挂一条不可见的宽条（`.sfp-resizer-grip`，宽 15 px = 3 倍把手宽、高 25% = 侧边栏高度的 1/4，以把手为圆心），左右各伸出 5 px、横跨侧边栏边界。
- 它能伸出边界，靠的是 **feed 模式下侧边栏不裁剪横向溢出**：`.sidebar-wrapper:has(> .sidebar-container.sfp-feed-mode)` 与 `.sidebar-container.sfp-feed-mode` 都设成 `overflow: visible !important`。
  - 原先这两处是 `overflow-x: hidden !important`。其中 `.sidebar-container` 那条本来就和 Discourse 自己的 `overflow-x: hidden`（`common/base/sidebar.scss`）同值，等于没做事；`.sidebar-wrapper` 那条把 `overflow-y: auto` 派生出的 `auto` 钉成 `hidden`，作用是防止横向滚动条。
  - 但 `overflow-x: visible` 与 `overflow-y: auto` 不能共存（`visible` 会被计算成 `auto`），所以两轴都得放开。
  - 放开是安全的：feed 模式里 `scrollHeight === clientHeight`（`.sfp-feed-container` 是 `height: 100%` + `overflow: hidden`），没有纵向滚动可丢；自己的 UI 由 `.sfp-feed-container` 与 `.sfp-settings-shell` 各自裁住；真站实测页面级 `scrollWidth === clientWidth`，不产生横向滚动。
- 因为不再需要逃出裁剪上下文，命中条直接作为 `.sfp-resizer` 的子节点，`mousedown` 冒泡回把手——没有 `body` 挂载、没有 `position: fixed`、没有滚动/尺寸同步。

### 2. 高度与钳制

设：

- `available` = `feedContainer.clientHeight - feedScroll.offsetTop - divider.offsetHeight`，即容器净高减去固定部分（头部/标签/筛选）与分隔线
- `mainMin` = 主列表**最顶上**那条的高度，缺失时 64 px
- `laterMin` = 稍后再读**最底下**那条的高度，缺失时 56 px

  两边都取「最靠近分隔线的那一条」：条目高度并不统一（预览卡片、话题条目、有无摘要都不同），取最靠近线的那条才不会算出一个两边都对不上的数。每次 `render()` 与预览落地后都会重算。

`available` 不能用 `feedScroll.offsetHeight + section.offsetHeight`：区域一旦溢出容器，那个和会跟着虚高，永远钳不住。`feedScroll.offsetTop` 在区域显示期间只由固定部分决定，所以稳定（`.sfp-feed-container` 是 offsetParent）。

规则：

1. 若 `available < mainMin + laterMin`：`section.height = floor(available / 2)`，分隔线锁定（不可拖、方向键无效），即「固定在中间对半分」。
2. 否则 `section.height = clamp(desired, laterMin, available - mainMin)`。
3. 每次显示、渲染、窗口尺寸变化、信息流头部重建后重新钳制；钳制不改变 `desired`，窗口恢复后回到用户值。
4. 拖拽：`pointerdown` 记录起点，`pointermove` 按 `clientY` 换算，`pointerup` 持久化。不使用 pointer capture，监听挂在 `document` 上，便于统一清理与合成事件测试。拖拽与键盘共用同一个 `clampHeight()`，与自动高度不会算出两套边界。
5. **改高度只改变可见窗口**：`setSectionHeight()` 只写 `style.height`，不碰 `scrollTop`，也没有任何「贴底」调用。内容之所以不动，是 `column-reverse` 让滚动原点落在底部（§一.2）：底边固定，高度变化只让上方多露出更早的条目。早先靠 `pinToBottom()` 每次改完强制滚动，滚到顶部再拖分隔线就会跳到底部——补丁式措施，已彻底移除。
6. 键盘：分隔线 `ArrowUp`/`ArrowDown` 每次 16 px，`Home`/`End` 到最小/最大；同步 `aria-valuemin/max/now`；锁定时 `aria-disabled="true"`。
7. 布局变化后通知控制器 `_scheduleHeadActionStateSync()`：信息流视口高度变了，回顶按钮的「离开首屏」判定需要重算。
8. 容器小到连固定部分都放不下（`available <= 0`）时不做任何钳制，保留上一次的值；这种情况下面板本身已不可用。
9. 列表清空时清掉持久化的高度，下次从「一个条目高」重新开始，而不是沿用上次拖出来的尺寸。

### 3. 自动高度

`desired` 由「是否拖动过」决定：

- **从未拖动**：`desired = 最底下那条的高度`。加第二条**不**自动长高——想多看一条就自己拖分隔线（超出的部分在区域内滚动）。
- **拖动过**：`desired` 固定为持久化的 px 值，此后不随条目数增减变化（移除到只剩一条时仍由 `laterMin` 保底）。

`itemHeight` 取区域里第一个条目的 `offsetHeight`（话题条目与预览卡片不同高，以先出现的为准），缺失时用 64 px。

### 4. 默认值

- 首次加入时按 §八.3 的一条高度出现，不做高度动画。
- 空列表时的拖拽占位区使用同一高度，松开后直接变成列表。

- 面板关闭（feed mode off）时区域消失，数据保留；再次开启恢复。

### 4. 文案

- 新增词条同时补齐 `zh-CN` 与 `en`；`getUiLocale`、`t` 与 `formatRelativeTime` 的既有行为不变。
- 页面语言变化时重渲染区域文案；预览卡片不重新拉取（它是加入时的快照）。已保存话题的 `fancy_title` 由 §五 的刷新同步按当前请求语言更新。

## 十三、已知边界

- 预览卡片是加入时的快照：站点修改话题标题或摘要后，卡片不跟随（只有话题快照随 §五 更新）。
- 语言切换后，预览卡片保持加入时的语言；区域文案会更新。
- localStorage 配额或隐私模式可能使列表仅存在于当前会话。
- 仅同 origin；子域或 `http`/`https` 差异视为不同站点，列表不共享。
- 面板关闭时不可见，也不能加入；这是「侧边栏内第二空间」的直接结果。
- 拖放是唯一加入方式；触摸设备与键盘用户没有等价入口。
- 删除与排序也只有拖动：没有按钮，也没有键盘等价操作。触摸设备上等于无法删除。
- 分隔线的可点区域仍然只有那两个 30 px 的圆：线本身在圆的上下方之外仍是 3 px 高。鼠标在线的中段与两端之外的位置，命中依然偏窄。
- 从昵称/用户名拖出依次尝试指针位置、`target` 祖先与文本选区；若浏览器三者都指不到发布者 span，仍会退回话题链接。
- 区域内的拖动依赖 `application/x-sfp-read-later` 私有类型；若某浏览器在 `dragover` 期间读不到 `types`，会退回「当成新链接」——此时拖出区域不会删除，而是重新加入（`add` 合并并移到最新，不会重复）。
- 右侧 5 px 的宽度拖拽手柄会覆盖分隔线最右端，分隔线其余部分仍可拖拽。把手中间那条 15 px 宽的隐形判定条横跨边界，会吃掉边界两侧各 7.5 px 内的点击——它是透明的，但确实压在那里。
- feed 模式下侧边栏不再裁剪横向溢出。自己的 UI 已由 `.sfp-feed-container` 与 `.sfp-settings-shell` 各自裁住，但任何**将来**放进侧边栏、又指望被侧边栏裁掉的元素都会直接溢出到主内容区。
- 跨标签页写入可能互相覆盖（最后写入生效）；不做字段级合并。
- `/onebox` 的「同一用户一个预览」限制会让批量加入排队；排队期间条目显示降级卡片。
- `refresh=true` 每次都让服务端重新生成预览，不复用 onebox 缓存；换来的是一旦某 URL 曾被缓存成纯 `<a>` 兜底，也不会永久卡在降级卡片上。
- 登录态在页面加载时判定：同一页面内登录或登出后 `availability` 不变，直到下一次刷新（探测读的是 `User.current()`，它只在启动时创建）。
- 匿名访客永远看不到预览卡片，即使 `/onebox` 其实允许匿名（当前实现不为此发试探请求）。
- **OG 回退的真实成本在网络上**（2026-10-25 实测 linux.do，Chrome + 已登录）：
  - 话题页 `/t/topic/3071498`：整页 795 KB、耗时 ~1070 ms；head 53 KB；只解析 head 1 ms，解析整页 8 ms。
  - 用户页 `/u/Jong`：743 KB / ~762 ms，`og:title` = 用户名，`og:image` = 头像，**无 `og:description`**。
  - 分类页 `/c/develop/4`：820 KB / ~1086 ms，`og:title` = 分类名，`og:description` = 分类说明，`og:image` = 分类图。
  - 所以回退会为每条失败链接多花一次 ~1 s / ~800 KB 的同站请求。它只发生在 onebox 已经失败之后，但批量加入时会把网络占用翻倍。
- OG 回退拿不到 onebox 才有的字段：没有 `blockquote`（话题首楼摘要）、没有分类徽章；用户页没有描述。这些情况下卡片只有标题与头图。
- OG 回退同样受「预览是快照」约束：站点改标题后卡片不跟随，直到条目被删掉重加。
